## 2. Pipeline

### 2.1 Ingest (`make ingest`)
- Read `corpus/corpus_manifest.csv` (columns in CONTRACT.md 6). For rows with a
  non-empty `text_file` and a non-empty file: load `corpus/<text_file>`.
- Parse and strip the 2-line header (`SOURCE:`, `RETRIEVED:`); keep `body_offset` so all
  span offsets refer to the full stored file.
- Record `{doc_id, jurisdictions, url, source_type, capture, retrieved_at, sha256,
  text_available, body_offset, text}` in `outputs/docs.jsonl`. The manifest `sha256` does
  not match the text files (it hashes the original capture, see NOTES.md): store it as
  `source_sha256`, compute our own `text_sha256` and use that for integrity and cache keys.
- Documents without text (link-only, check-terms, empty D056) are recorded with
  `text_available=false`; never extracted; may appear in the UI as "further reading".
- If `data/supplement/manifest.csv` exists, ingest it the same way with
  `capture=manual`.

### 2.2 Chunk
- Split by legal structure first (`§`, `Section`, `Sec.`, numbered subsections like
  `6.`, `b.`), then by size (~6k tokens, 500-token overlap). Web pages: drop obvious
  navigation lines (very short repeated lines) before chunking, but keep offsets.
- Chunk keeps `doc_id, chunk_id, char_start, char_end, heading`.
- Large docs (D067 160 KB, D049 56 KB) produce many chunks; that's expected.

### 2.3 Extract (`make extract`) — the only LLM stage for rules
- `llm.py`: provider-agnostic, structured output, temperature 0, disk cache keyed by
  `(sha256, chunk_id, prompt_version, model)`, `--no-cache` for live reruns, every call
  logged to `audit.jsonl`.
- Prompt `prompts/extract_v1.md` includes:
  - the 6 categories with one-line definitions and the guide's "what to capture" per category
  - the schema and `sample_rule_record.json` as the example
  - the document's manifest jurisdiction (`"CA"` or `"City, ST"`) and level, so the model
    does not guess them; a document can still cite a state statute (e.g. a city page
    summarizing state law) and then the rule's jurisdiction is the state
  - per rule: title, requirement (1-2 plain sentences), key_value, coverage conditions as
    text **and** as predicates over allowed facts (2.5), exemptions, citation, status
    hint (enacted / bill or proposal / failed), penalty if stated, and `quoted_span`
    copied verbatim (1-3 sentences containing the requirement)
  - effective date as **two fields**: `effective_date_phrase` (verbatim: "shall take
    effect on the first day of the twelfth month next following the date of enactment")
    and `effective_date_anchor` (verbatim date the phrase depends on: "approved July 20,
    2026", "Chaptered 10/06/25"), or an explicit date if stated
  - "interaction" language copied verbatim when present ("exempt if subject to local rent
    control", "a municipality shall be prohibited from enacting an ordinance that
    conflicts with this act")
  - if a field is not stated, return null; never infer. If the chunk has no rule in the
    6 categories, return an empty list.
- Output `outputs/candidates.jsonl` with provenance.

### 2.4 Dates (`navigator/extract/dates.py`, deterministic)
Named, unit-tested rules turning phrase + anchor into ISO `effective_date`:
- `explicit_date` ("went into effect on October 14, 2024")
- `first_day_of_nth_month_after(anchor, n)` (NJ FAIR Act → 2027-07-01)
- `days_after(anchor, n)`
- `ca_default_jan1_next_year(chaptered)` (CA bills with no stated date → 2026-01-01).
  This rule is not in the corpus text, so it sets `needs_review` with reason
  "California default effective date for non-urgency statutes" and lowers confidence.
- Unparseable → `effective_date: null`, `needs_review`.
Rule `status` for the default query date is then computed: bill/proposal → `pending`;
failed → `failed`; enacted with `effective_date > 2026-10-01` → `not_yet_effective`;
else `in_force`. The engine recomputes status for other query dates.
**Two sources, two dates** for the same rule (Berkeley ch. 13.63, LA RSO formula): keep
the date from the official primary text, set `conflict_flag: true` and `conflict_note`
naming both dates and both sources. This surfaces the guide's section-9 open questions.

### 2.5 Verify (`make verify`) — deterministic gates
Rejecting (first failure rejects; reason logged to `rejects.jsonl` and `audit.jsonl`):
1. Schema validation (`RuleRecord`).
2. Span: `quoted_span` ≥ 20 chars and found in the document body. Exact normalized match
   (NFC, whitespace collapsed) first, then tolerant (quote styles, hyphenation, `§`
   spacing) at similarity ≥ 0.95. Store `span_start`, `span_end` in full-file offsets.
3. Enums: category, level, status.
4. Source fields: `source_doc_id`, `source_url`, `retrieved_at` copied from the manifest.
Non-rejecting (lower `confidence`, add to `review_reasons`, `needs_review: true`):
5. Date phrase not found within 1,000 chars of the span, or anchor not found anywhere in
   the document (approval/chaptering anchors sit in the bill header, e.g. D069).
6. A number in requirement / key_value / coverage / penalty that is not in the span or
   its neighborhood.
7. Predicates referencing facts outside the allowed list are dropped; coverage marked
   needs review.
8. The rule's jurisdiction differs from the document's manifest jurisdiction and is not a
   state-law citation.
Then:
9. Dedup/merge: same (jurisdiction, category, citation) → keep longest verified span,
   union exemptions, keep all source_doc_ids in internal provenance.
10. Precedence linking: resolve verbatim interaction language into `overrides`
    (team_rule_ids) + `interaction` text (direction), e.g. state rent cap ↔ city rent
    control in the same state and category, FAIR Act ↔ JC/Hoboken bans.
11. Write `rules.json` (`{"rules": [...]}`, schema fields only) and `rules_internal.json`.

### 2.6 Facts and coverage (`navigator/engine/facts.py`, `coverage.py`)
Facts from `sample_addresses.csv`: `year_built`, `units`, `use_code`,
`use_description`, plus resolved `state`, `city`.
- `units_min`/`units_max`: from `units` if present, else parsed from `use_description`
  with `config/unit_parsers.yaml` (CONTRACT.md 7). `units_source` recorded.
- Not available: owner type, certificate-of-occupancy date, rent, tenancy facts.
Predicate form: `{fact, op, value}` with `<, <=, >, >=, ==, in, not_in`, combined with
`all`/`any`/`not`. Three-valued logic (missing → UNKNOWN). Unit tests use interval logic
on `units_min`/`units_max`.
**Certificate-of-occupancy cutoffs** (guide 4.1): a predicate on
`certificate_of_occupancy_date <= D` is evaluated from year built:
built after D's year → FALSE; built before D's year → TRUE with reason "derived from
year built" (lowers confidence); built in D's year → UNKNOWN; missing → UNKNOWN.
The cutoff date `D` always comes from the extracted rule, never from config.
Owner-type conditions → UNKNOWN, with one exception: if the law's own text ties the
exemption to the building's unit count (e.g. "owner-occupied premises with 2 or fewer
units") and the building's `units_min` is above that limit, the exemption cannot apply
and the condition is decided. Write the reason in the explanation either way.

### 2.7 Geocode and jurisdiction (`make geocode`)
- Census Geocoder batch (package `censusgeocode`) with geographies for all 500 rows in one
  batch (limit 10,000). Use street, postal city, state, zip.
- Legal city = Census incorporated place (cross-check with county subdivision in NJ and
  MA). **Never use `postal_city`** to decide the city (Dorchester, Roxbury, San Ysidro...).
- `config/jurisdictions.yaml` built from returned place names ("Boston city, MA" →
  "Boston, MA"), checked by hand against the 9 cities.
- Unmatched: retry single-line; then TIGER/Line point-in-polygon if coordinates exist;
  else keep postal city with `jurisdiction_confidence: low`, `needs_review`, and a
  reason in every explanation for that address.
- Address outside all 9 cities (possible for edge ZIPs): state rules only; city rules
  omitted; explanation says so.
- Output `outputs/parcels.json`: `{address_id, street_address, postal_city, state, city,
  lat, lng, geoids, jurisdiction_confidence, year_built, units, units_min, units_max,
  units_source, use_code, use_description, missing_facts}`.

### 2.8 Engine (`make lookups`)
For each address and each rule whose jurisdiction is the address's state or city:
```
status_on(as_of):  failed -> skip;  pending -> PENDING;
                   effective_date > as_of -> NOT_YET_EFFECTIVE;  else in force
in force:  cov = coverage(rule, facts)
           FALSE   -> omit
           UNKNOWN -> UNKNOWN (+ missing facts)
           TRUE    -> SUPERSEDED if a stricter rule at the other level governs, else APPLIES
```
- Superseded: only from `overrides` + `interaction` on the records. If the governing rule's
  coverage is UNKNOWN, the yielding rule is UNKNOWN ("may be superseded by r-…"), never
  dropped.
- Conflict flag on a lookup row: the rule has `conflict_flag` and the conflicting rule also
  covers this address on this date, or the T3 pattern (state law with a municipal
  preemption clause + a city rule in the same category in the address's city).
- `explanation` (deterministic, `explain_lookup.py`): one sentence naming the deciding
  fact(s), exemption, supersession or missing fact, e.g. "Built 1962, before the
  ordinance's certificate-of-occupancy cutoff year (derived from year built)."
- Reasoning boundary (`boundary.py`): `checked` / `not_checked` lists per row.
- Confidence (`confidence.py`): deterministic 0-1 from span match type, date method,
  derived facts, jurisdiction confidence; reasons listed. No LLM self-ratings.
- Outputs: `lookups.json` for all 500 (`{"as_of": "2026-10-01", "lookups": {...}}`,
  `[]` for addresses with nothing), `timeline.json` (per address, dates where any result
  changes), `snapshots.json` (for key dates = all distinct effective dates + 2026-10-01:
  per address, per category, winning result + conflict flag) for the frontend slider.

### 2.9 Change tracking (`make changes`)
- `matcher.py` maps each test's `rule_ids` to our rules using the test's `states`, the id
  pattern (`ALG` → algorithmic_rent_setting, `RENT` → rent_increase_limits, `P` →
  pending/failed, city prefix `HOB`/`JC`) and status. Writes `config/test_rule_map.yaml`
  for one human review. No match → the test's notes say so; nothing is invented.
- `tracker.py` per test type:
  - `as_of` (T1, T3): results at `as_of_before` and `as_of_after`; affected = addresses
    whose result for the mapped rule changes. T3 conflict ids = addresses where the
    mapped state rule and a mapped `conflict_with` city rule both cover the address.
  - `boundary` (T2): affected = addresses where each city rule applies; assert none in
    Newark; flag any address whose legal city differs from postal city.
  - `pending` (T4): evaluate coverage as if enacted; affected = addresses covered; lookups
    still say `pending`.
  - `negative` (T5): assert no `rent_increase_limits` rule applies in Boston or Cambridge;
    affected = []; record the failed measure if a citable span exists, else note it.
- Expected behaviors from `change_tests.json` (CONTRACT.md 5) become assertions in
  `tests/test_changes.py` and pass/fail lines in `make eval`.
- Write `changes.json` (all five keys, `conflict_flag_address_ids` always present) and
  `scores/changes_report.txt`.

### 2.10 Plain-language layer (`navigator/explain/plain.py`, build time)
Per rule: `answer_tenant`, `answer_owner` — one sentence, ≤ 20 words, starts with the
answer, says "you", generated only from `quoted_span` + structured fields.
Guards: number guard (every number/date/%/$ occurs in the span, else drop → UI shows the
quote); evasion guard (no "avoid", "get around", "loophole", ways to qualify for an
exemption). Spanish (stretch): translate the approved English sentence, same guards.
Output `summaries.json`. These are UI text only; `lookups.json` explanations come from 2.8.

### 2.11 Audit log
`audit.jsonl`: `{ts, stage, doc_id, chunk_id, model, prompt_version, input_sha,
output_sha, decision, reason}` for every LLM call, verify decision, date resolution,
change run and ingest. "Keep an audit log so another person can reproduce the result."

## 3. API (FastAPI, `make api`)

Every response: `as_of`, `generated_at`, `disclaimer: "Not legal advice."`.
```
GET  /health
GET  /resolve?lat=&lng=        -> {state, city, nearest_address_id within 30 m or null}
GET  /search?q=                -> addresses by street text or ZIP (ZIP only moves the map)
GET  /lookup?address_id=&as_of=&role=tenant|owner&lang=en
POST /lookup {lat, lng, facts, as_of, role}  -> live engine run with user-entered facts
GET  /rule/{team_rule_id}      -> record + text window + span offsets + source_url + retrieved_at
GET  /timeline?address_id=     GET /snapshots
GET  /changes                  GET /changes/{test_id}
GET  /audit?team_rule_id=
GET  /eval                     -> scores/eval_latest.txt
POST /ingest                   -> streamed progress for a new document
```

## 4. Evaluation (`make eval`) — our scoring loop

No scoring script is supplied, so `eval/run_eval.py` measures us and writes
`scores/eval_latest.txt` + `scores/history.jsonl`. Present results honestly as a
self-evaluation.

1. **Format validity (must be 100%):** three files validate; lookups cover all 500
   address ids; changes has T1-T5.
2. **Grounding (must be 100%):** every `quoted_span` is found in its `source_doc_id`; every
   `applies` row's rule has span, citation, source_url, retrieval date.
3. **Brief recall checklist:** `eval/brief_checklist.yaml` lists the laws the briefs name
   per category (e.g. Cal. Civ. Code §§1947.12, 1946.2, 1950.5, 1950.6; Gov. Code §12955;
   N.J.S.A. 2A:18-61.1, 46:8-21.2; P.L.2025 c.405; NJ Fair Chance in Housing Act; NJ FAIR
   Act; MA G.L. c.186 §15B, c.40P §4, c.112 §87DDD½; SF §37.10C; San Diego
   §§98.1101-98.1104; Berkeley ch. 13.63; MA S.2983, H.5222), each marked
   `text_in_corpus: yes/no` from the manifest. Report found / missing for those with text.
   Evaluation data only; the pipeline never reads it.
4. **Gold set (team-built, first hours):** ~15 rules in `eval/gold_rules.json` and ~20
   addresses in `eval/gold_addresses.json`, copied from corpus text and checked on the
   Census Geocoder. Cover all 3 states, all 6 categories, and these cases: an SF building
   built before 1979 (superseded state cap), an LA building, a San Diego or Berkeley
   building (unknown year), a Boston row with a neighborhood postal city, a Cambridge row,
   Hoboken, Jersey City, Newark. Metrics: rule match on (jurisdiction, category, citation);
   field accuracy on effective_date, status, key_value, citation; address result accuracy
   with "missed applies" counted separately (the worst error).
5. **Change tests:** each expected behavior in `change_tests.json` as pass/fail, plus
   affected-set sizes (T1 = 250, T3 = 140, T4 = 110, T5 = 0, T2 = Hoboken + JC counts).
6. **Coverage matrix:** rules per (jurisdiction, category); a cell is red if the checklist
   names a law there with text in the corpus but we have no rule.
7. **Jurisdiction check:** share of addresses whose legal city ≠ postal city; all resolve to
   one of the 9 cities or are flagged.
8. **Determinism:** two runs from cache give byte-identical outputs.

## 6. Scalability path (put in README and METHOD.md)

New jurisdiction = add its documents to the manifest (or supplement), add its Census place
to `config/jurisdictions.yaml`, run `make all`. No code changes. Stretch goal: do this live
for one new city using public official text, captured one page at a time within site terms.

## 7. Out of scope

Vector DB, RAG, Obsidian, knowledge graphs, agent frameworks; LLM calls while users click;
training or fine-tuning; scraping code-publisher sites; computing CPI or fee amounts not in
the corpus; a free-form chat box.
